# Run 20261124T2336Z-7b3e (session 12)

**Ticket:** [#13](https://github.com/anotherhale/str-ready-room/issues/13) — ADR-011,
notification channels/preferences and audit retention.

## What was decided

The ticket's real question is not "which channels" but "which of these two records
needs which guarantee". Notifications and audit look alike and need opposite
properties, so ADR-011 splits them:

| | Audit entry | Notification |
|---|---|---|
| Written | inside the mutating transaction | after that transaction commits |
| On failure | the action rolls back (`503 audit_unavailable`) | logged, counted, dropped |
| Reader | `audit:read` (squadron admin only) | the recipient, and nobody else |
| Retention | indefinite, authorized deletion | 90 days unread / 30 days after read |

Everything else follows from that split: the audit record shape and its
allowlisted `changes` delta, the coverage map (writes and denials, never reads),
seven notification event kinds with a label-key envelope, recipient resolution
as a subset of the ADR-006 visibility policy, aggregation and read state,
preferences with two non-disableable duty events, retention, and access control.

Acceptance scenario 14 becomes structural: emission is post-commit and nothing
derives work state from `read_at`, so a lost notification cannot mark a task
acknowledged or complete.

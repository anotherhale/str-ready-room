## What the ADR settles

| Question | Decision |
|---|---|
| Record shape | `workflow_runs` (current state) + append-only `workflow_run_events` + `workflow_run_steps` (one row per idempotent unit) |
| Catalog | fixed enum of seven workflow types, each declaring whether it can produce a consequential step |
| States | `queued → running → waiting_approval → succeeded / failed / cancelled`, transitions enumerated with a `reason_code`; terminal never reopens |
| Approval durability | `waiting_approval` is row-backed; execution needs an `approved` row whose `action_digest` still matches the recomputed proposal; expiry/denial/change fails the run |
| Idempotency | unique `(squadron_id, idempotency_key)` on run creation, unique `(run_id, step_key)` on step claim — plain constraints, portable to SQLite and PostgreSQL |
| Retries | 3 attempts/step, 5 s then 30 s, 20 steps, 15-minute deadline, 1 recovery attempt; authorization/validation never retried |
| Cancellation | cooperative at step boundaries; an in-flight step finishes and records its result |
| Recovery | 15 s heartbeat, 30 s staleness sweep, resume from the last recorded step, `recovery_unsafe` instead of guessing |
| History retention | run history is the operational audit trail; payloads are references and digests only |
